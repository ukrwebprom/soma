> Актуально на 3 августа 2026 года.  
> Этот файл предназначен для размещения в корне репозитория. Он описывает продукт, текущую архитектуру, реализованные части, согласованные решения и ближайший план разработки.

---

## 1. Назначение проекта

**SOMA Certificates** — отдельный сервис для выпуска, проверки и погашения цифровых сертификатов.

Изначально SOMA создавалась как часть маркетинговой игры для NEMO: пользователь набирает очки, обменивает их на сертификат, показывает QR-код сотруднику заведения, а сотрудник проверяет и погашает сертификат.

Продуктовая идея расширена: SOMA должна работать и **вне игры** как самостоятельная система для:

- одиночного выпуска сертификатов;
- массового выпуска сертификатов;
- отправки сертификатов через мессенджеры и email;
- рекламных акций и промо;
- работы с продавцами/операторами;
- контроля погашений;
- аудита и выгрузки данных.

Основной бизнес-процесс:

```text
Шаблон
→ выпуск одного сертификата или пакета
→ изображение с QR
→ передача пользователю
→ сканирование QR
→ проверка статуса
→ ввод PIN оператора
→ одноразовое погашение
→ запись в журнале
```

---

## 2. Архитектурное решение: single-tenant

SOMA сейчас проектируется как **single-tenant продукт**:

- одна установка обслуживает одного клиента;
- у каждой установки отдельные backend, база и storage;
- модель `Organization` не используется;
- многопользовательская SaaS-архитектура пока не нужна;
- для нового клиента разворачивается отдельный экземпляр.

Это решение следует сохранять, пока явно не принято другое.


### 7.2. Certificate

```prisma
model Certificate {
  id                     String
  templateId             String
  template               CertificateTemplate
  code                   String

  title                  String
  description            String?
  terms                  String?
  instructionText        String?

  coverPortraitUrl       String?
  coverLandscapeUrl      String?
  logoUrl                 String?

  status                 CertificateStatus

  issuedAt               DateTime
  expiresAt              DateTime
  redeemedAt             DateTime?

  redeemedByOperatorId   String?
  redeemedByOperator     Operator?

  updatedAt              DateTime
}
```

```prisma
enum CertificateStatus {
  ACTIVE
  REDEEMED
  REVOKED
}
```

### EXPIRED вычисляется

`EXPIRED` не хранится в Prisma enum.

Он определяется так:

```text
status === ACTIVE
и
expiresAt <= now
```

API может возвращать эффективный статус `EXPIRED`, но база продолжает хранить `ACTIVE`.

### Snapshot шаблона

При выпуске в сертификат копируются:

- `title`;
- `description`;
- `terms`;
- `instructionText`;
- `coverPortraitUrl`;
- `coverLandscapeUrl`;
- `logoUrl`.

Это обязательное решение: исторические сертификаты не должны менять содержимое после редактирования шаблона.

### 7.3. Operator

```prisma
model Operator {
  id                     String
  name                   String
  pinLookup              String
  pinHash                String
  isActive               Boolean
  redeemedCertificates   Certificate[]
  createdAt              DateTime
  updatedAt              DateTime
}
```

Оператор — сотрудник, погашающий сертификаты. Это не администратор системы.

Термин в UI:

```text
Оператори
```

Первый тестовый оператор:

```text

```

## 8. PIN оператора

PIN состоит из четырёх цифр.

При создании backend:

1. генерирует PIN;
2. создаёт `pinLookup`;
3. создаёт защищённый `pinHash`;
4. сохраняет только lookup и hash;
5. возвращает открытый PIN один раз.

При проверке:

1. вычисляется lookup;
2. оператор ищется по lookup;
3. проверяется `isActive`;
4. PIN сравнивается с hash;
5. наружу возвращаются только `id` и `name`.

Деактивированный оператор не может погашать сертификаты.

Позже добавить:

- rate limiting;
- ограничение попыток PIN;
- одинаковую внешнюю ошибку для неверного и деактивированного PIN;
- аудит подозрительных попыток.

## 10. Проверка сертификата

Известный публичный endpoint:

```http
GET /api/certificates/verify/:code
```

Проверка:

```text
поиск по code
→ вычисление effectiveStatus
→ valid = effectiveStatus === ACTIVE
→ возврат безопасных публичных данных
```

Публичный ответ может содержать:

- `code`;
- `title`;
- `description`;
- `terms`;
- `status`;
- `issuedAt`;
- `expiresAt`;
- `redeemedAt`;
- `valid`.

Не возвращать внутренние hashes, secrets и административные данные.

## 12. Погашение

Погашение должно быть атомарным:

```text
code совпадает
status = ACTIVE
expiresAt > now
→ status = REDEEMED
→ redeemedAt = now
→ redeemedByOperatorId = operator.id
```

Использование условного `updateMany` и проверки `count` защищает от одновременного двойного погашения.

После успеха вернуть сертификат и оператора (`id`, `name`).

Backend должен различать:

- не найден;
- уже погашен;
- отозван;
- просрочен;
- неверный PIN;
- оператор деактивирован.

### Сценарий UI

1. Оператор сканирует QR.
2. Видит активный сертификат.
3. Нажимает `Погасити сертифікат`.
4. Вводит PIN.
5. Backend проверяет оператора.
6. Сертификат атомарно погашается.
7. Страница показывает время и имя, например `Марина`.
8. Повторное сканирование показывает `REDEEMED`.

Фактически подключённый route:

```http
POST /api/certificates/:code/redeem
```

Он принимает `{ "pin": "4831" }`, проверяет активного оператора и вызывает атомарную service-логику погашения.

- действие `Активувати` / `Деактивувати` подключено к существующему `PATCH /api/admin/operators/:id/status`; на время запроса пункт блокируется, после успеха строка обновляется на прежней позиции без пересортировки таблицы, а ошибка API показывается над таблицей;
- действие `Змінити PIN` открывает модальное окно: администратор может ввести собственный четырёхзначный PIN или включить `Згенерувати випадковий PIN`, при этом ручное поле блокируется;
- `POST /api/admin/operators/:id/reset-pin` принимает необязательное поле `pin`: без него генерирует случайный уникальный PIN, с ним валидирует четыре цифры, безопасно пересчитывает lookup/hash и возвращает конфликт, если PIN уже занят;
- после успешной замены новый PIN показывается один раз в состоянии успеха и удаляется из состояния frontend при закрытии окна.

## 19. Журнал погашений — согласованная функция

Отдельная страница:

```text
Журнал погашень
```

Назначение:

- что погашено;
- дата и время;
- кто погасил;
- тип сертификата;
- код.

Обратный хронологический порядок:

| Дата і час | Сертифікат | Код | Оператор |
|---|---|---|---|
| 03.08.2026, 14:32 | Безкоштовна піца | Xy7mUG… | Марина |

При клике желательно открывать существующий drawer сертификата.

### Отдельная таблица пока не нужна

Успешное погашение уже хранится в Certificate:

- `status = REDEEMED`;
- `redeemedAt`;
- `redeemedByOperatorId`;
- `title`;
- `code`;
- `templateId`.

Запрос:

```ts
where: {
  status: "REDEEMED",
  redeemedAt: { not: null },
},
orderBy: {
  redeemedAt: "desc",
},
```

Использовать snapshot `certificate.title`.

### Планируемый endpoint

```http
GET /api/admin/redemptions
```

### Изменение от 3 августа 2026: первая версия журнала

- подключён `GET /api/admin/redemptions?page=1&limit=30`;
- endpoint читает погашенные сертификаты без отдельной таблицы событий, выбирает только безопасные поля сертификата, оператора и шаблона, сортирует по `redeemedAt desc` и возвращает серверную пагинацию;
- в админ-навигацию добавлен раздел `Журнал погашень` с route `/redemptions`;
- страница показывает дату и время, snapshot-название сертификата, сокращённый код и оператора;
- реализованы loading, empty, error и переходы между страницами;

## 20. Пакетный выпуск — согласованная функция

SOMA должна уметь создавать пакет, например 100 сертификатов.

### Решение по лимиту

Основной лимит задаётся размером пакета, а не шаблоном.

```text
Шаблон: Безкоштовна піца
Пакет «Літня акція»: 100
Пакет «Осіння акція»: 200
```

Глобальный `issuanceLimit` у шаблона пока отложен.

### Планируемая модель

```prisma
enum CertificateBatchStatus {
  PENDING
  GENERATING
  READY
  FAILED
}

model CertificateBatch {
  id          String
  templateId  String
  name        String?
  quantity    Int
  status      CertificateBatchStatus
  archiveUrl  String?
  errorText   String?
  createdAt   DateTime
  completedAt DateTime?
}
```

В Certificate:

```prisma
batchId String?
batch   CertificateBatch?
```

### Сценарий

1. Выбрать шаблон.
2. Нажать `Створити пакет`.
3. Ввести название.
4. Ввести количество.
5. Указать общую дату окончания.
6. Создать записи.
7. Сгенерировать PNG.
8. Добавить PNG в ZIP.
9. Добавить CSV.
10. Загрузить ZIP в Supabase.
11. Показать download.

Архив:

```text
pizza-summer-100.zip
001_A7kd9....png
002_Hm31x....png
...
100_Vz77q....png
certificates.csv
```

CSV:

```csv
number,code,expiresAt,verificationUrl
1,A7kd9...,2026-09-30,https://...
```

### Хранение

Не загружать каждый PNG отдельно.

Рекомендуется:

- генерировать последовательно;
- сразу добавлять в ZIP;
- не держать весь пакет в памяти;
- хранить только итоговый ZIP;
- отдельный PNG получать существующим image endpoint.

### Асинхронность

Не держать обычный HTTP-запрос до окончания генерации.

Планируемый endpoint:

```http
POST /api/admin/certificate-batches
```

Пример body:

```json
{
  "templateId": "...",
  "name": "Літня акція",
  "quantity": 100,
  "expiresAt": "2026-09-30T20:59:59.999Z"
}
```

Быстрый ответ:

```json
{
  "batchId": "...",
  "status": "PENDING"
}
```

Frontend показывает прогресс:

```text
Генерується…
38 із 100
```

### Срок действия

Для первой версии использовать фиксированную дату окончания всего пакета.

Не считать `validityDays` от момента массового создания: часть сертификатов может истечь до выдачи.

Активация при выдаче и статус `PREPARED` обсуждались, но не входят в MVP.

### Очередь

Механизм ещё не выбран.

Допустимы:

- простая очередь внутри процесса для single-instance MVP;
- jobs в PostgreSQL;
- отдельный worker позднее.

Не внедрять Redis без отдельного решения.

## 30. Актуализация административного интерфейса (2026-08-06)

### 30.1. Выбор одиночного или серийного создания

В форме создания сертификата по шаблону добавлен явный переключатель режима:

- `Один сертифікат` — режим по умолчанию;
- `Серія` — пакетное создание сертификатов.

Переключатель визуально использует те же классы, что переключатель портретной и лендскейпной ориентации изображения сертификата.

Поведение формы:

- в режиме `Один сертифікат` поле количества скрыто, а запрос отправляется на `POST /api/admin/certificates`;
- в режиме `Серія` справа от переключателя появляется поле `Кількість`;
- начальное значение количества для серии — `10`;
- серийный запрос отправляется на `POST /api/admin/certificates/batch` с параметром `quantity`;
- подпись `Кількість` расположена слева от поля ввода в одной строке;
- ширина переключателя определяется его содержимым, поле количества занимает оставшееся место строки.

Режим запроса определяется состоянием переключателя, а не косвенно значением количества.

### 30.2. Фильтр серий на странице сертификатов

На странице списка сертификатов фильтр называется `Серія` и имеет следующую семантику:

- `Усі сертифікати` — показывает все сертификаты, как входящие в серии, так и одиночные;
- `Без серії` — показывает сертификаты без `issueGroupId`;
- остальные пункты соответствуют конкретным `issueGroupId`, а их подпись формируется из причины создания серии.

Ранее первый пункт назывался `Усі серії`, а сертификаты без серии обозначались прочерком. Эти подписи заменены, чтобы фактическая логика фильтра была понятна пользователю.

В интерфейсе сохранены корректные формулировки, связанные с фактом создания сертификата: `Ручний випуск`, `Причина випуску`, `Дата випуску`, `Випуск сертифіката за шаблоном` и `Режим випуску сертифікатів`. Термин `Серія` используется для группировки сертификатов, а не как полная замена термина выпуска.

### 30.3. Дата и время погашения

В модели `Certificate` время погашения хранится в nullable-поле `redeemedAt`, сопоставленном с колонкой PostgreSQL `redeemed_at TIMESTAMPTZ(3)`.

При успешном атомарном погашении сервис одновременно:

- меняет статус на `REDEEMED`;
- записывает текущее время в `redeemedAt`;
- записывает `redeemedByOperatorId`.

В боковой панели сертификата строка `Погашено` показывает не только дату, но и время в украинской локали с точностью до минут. Журнал погашений также показывает `redeemedAt` в колонке `Дата і час` и сортируется от новых записей к старым.

### 30.4. Боковая панель журнала погашений

На странице `Журнал погашень` строки таблицы стали интерактивными. Клик по строке, а также клавиши Enter или Space открывают боковую панель выбранного погашенного сертификата. Escape, кнопка закрытия и клик по затемнённой области закрывают панель; при открытой панели прокрутка страницы блокируется.

После открытия выполняется дополнительный запрос `GET /api/admin/certificates/:id`, чтобы дополнить краткую запись журнала полными данными сертификата.

Панель содержит:

- статус `Погашений`;
- уникальный код и компактную кнопку `Копіювати` рядом с ним;
- источник, причину выпуска, комментарий и идентификаторы серии/события;
- шаблон, дату выпуска, срок действия, дату и время погашения, оператора;
- описание и условия сертификата.

В отличие от панели на странице сертификатов, в панели журнала отсутствуют:

- превью изображения сертификата;
- переключатель ориентации;
- кнопка загрузки PNG;
- нижняя кнопка `Скопіювати код`.

Для строк журнала добавлены состояния наведения, клавиатурный фокус и курсор, показывающий возможность открытия деталей.

### 30.5. Единый информационный блок боковых панелей

В боковых панелях на странице сертификатов и в журнале погашений ранее отдельные секции `Деталі серії` и `Інформація` объединены в одну секцию `Інформація`. Все поля обеих секций сохранены внутри одного списка.

Идентификатор группы выпуска отображается в этом блоке с пользовательской подписью `ID серії`.
